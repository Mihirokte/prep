An eval is only as good as the dataset behind it, and the dataset is where most teams underinvest. A model change that scores plus three points on a stale, unrepresentative set tells you nothing about production. Building the set is the manual work Chip Huyen calls the highest ratio of value in all of evaluation. Interviewers ask about it because sourcing, sizing, and slicing a dataset is where the real judgement lives, scoring is comparatively mechanical.

## Where cases come from

Three sources, each with a different bias, and a strong set blends all three.

- **Production logs** are the ground truth for your real input distribution. They are the only source that reflects what users actually send, including the inputs you never imagined. The cost is labelling, and the risk is privacy.
- **Synthetic cases** are generated by a model from a schema or seed. Cheap and fast, good for covering a space systematically and for stress-testing before you have traffic. The risk is that they drift from real phrasing and over-sample the easy middle.
- **Expert-written cases** are hand-authored by someone who knows the domain. The most expensive and the most valuable for hard, rare, or high-stakes cases a log sample would miss.

```steps
Seed | Hand-write a small golden set that encodes known-good behaviour
Grow | Sample production logs to match the real input distribution
Augment | Add synthetic cases to cover gaps and edge inputs the logs miss
Harvest | Fold every real production failure back in as a permanent case
```

## How many, and how sure

Dataset size is a confidence question, not a round-number question. A pass rate measured on n cases carries sampling error, and the width of that error bar is roughly proportional to one over the square root of n. The practical consequence is sharp: moving from 100 to 400 cases roughly halves the error bar, but moving from 400 to 1600 only halves it again, so returns diminish fast.

> **Numbers.** A pass rate near 0.9 on 100 cases has a 95 percent interval of roughly plus or minus 6 points (illustrative, from the standard binomial error). To call a plus 2 point change real, you need a set large enough that 2 points sits outside the noise, which usually means several hundred cases per slice, not per suite.

A few hundred well-chosen cases that span your real traffic beat ten thousand near-duplicates. Volume without coverage buys false confidence.

## Slicing

A single aggregate score hides the failures that get you fired. Slice the set by the dimensions that matter: input language, query type, document source, user segment, short vs long input. A system can post 0.9 overall while sitting at 0.6 on the one slice that is your highest-value customer.

```bars
title: Aggregate hides a broken slice (illustrative)
unit: pass rate
Overall | 0.90
English queries | 0.94
Non-English queries | 0.61
Multi-hop queries | 0.58
```

The decision rule: gate on the worst important slice, not only the mean. The mean can rise while a slice you care about collapses.

## Contamination and leakage

Two distinct failures that both inflate your numbers.

- **Train/test leakage** happens when a case, or something near-identical, appears in both your few-shot prompt examples and your eval set. The model has effectively seen the answer, so the score is a memory test, not a generalisation test. Keep prompt examples and eval cases strictly disjoint.
- **Benchmark contamination** happens when a public benchmark leaked into the model's pretraining corpus. A frontier model can score high on a famous benchmark because it memorised it, not because it reasons. This is why a private, held-out set built from your own data is worth more than any public leaderboard number.

| Trap | Symptom | Fix |
|---|---|---|
| Prompt-example leakage | eval score far above production quality | disjoint example and eval pools |
| Benchmark contamination | strong on public set, weak on yours | hold out a private set from your own data |
| Over-easy synthetic | high score, real users still fail | mix in production logs and adversarial cases |

## Maintaining a golden set

The golden set is the stable, curated core you trust most: known-good cases, reviewed, versioned like code, and changed deliberately. Treat edits to it as commits with review, because silently editing the golden set is how a team fools itself into thinking quality improved. Grow it by harvesting production failures, retire cases that no longer reflect real usage, and re-balance slices as traffic shifts. A living golden set is a product asset, not a one-time deliverable.

```recall
Q: Why is a private held-out set worth more than a public benchmark score?
A: Public benchmarks can leak into a model's pretraining data, so a high score may be memorisation rather than reasoning. A private set built from your own data cannot have been seen and reflects your real distribution.
Q: Your eval set is 50 cases and a change scores plus two points. Why not ship on that?
A: With 50 cases the sampling error is far wider than two points, so the change is inside the noise. You need several hundred cases per slice before a two-point move is distinguishable from chance.
Q: What breaks if your few-shot prompt examples also appear in the eval set?
A: The model has effectively seen the answers, so the eval becomes a memory test and the score overstates real quality. Keep example and eval pools strictly disjoint.
Q: Why slice the dataset instead of reporting one aggregate pass rate?
A: An aggregate can stay high while a specific important slice, like non-English or multi-hop queries, collapses. Slicing surfaces the failure the mean hides so you can gate on the worst important slice.
Q: What is the role of synthetic cases if production logs are the ground truth?
A: Synthetic cases cover gaps and edge inputs systematically and let you build a set before you have traffic. They complement logs rather than replace them, because they can drift from real phrasing.
```

### The confidence arithmetic

Treat a pass rate as a proportion p measured on n independent cases. The standard error is sqrt(p times (1 minus p) divided by n), and the 95 percent interval is roughly p plus or minus 1.96 times that. At p = 0.9 and n = 100 the standard error is sqrt(0.09 / 100) = 0.03, so the interval is about plus or minus 0.06. At n = 400 it falls to about plus or minus 0.03, at n = 1600 to about plus or minus 0.015. Two lessons fall out. First, to detect a small improvement you need the interval narrower than the improvement, which sets your minimum n. Second, because the error scales with one over sqrt(n), each halving of the error bar costs four times the cases, so there is a natural ceiling past which more data is not worth the labelling. These are illustrative applications of the standard binomial error, not a benchmark result.

### Sourcing without poisoning privacy

Production logs are the best source and the most dangerous. Before a real user input enters an eval set, strip or redact PII, and prefer to store a reference and a derived label rather than raw sensitive text. For regulated domains, keep the eval set inside the same trust boundary as the production data and do not ship it to a third-party eval service without checking the data agreement. The engineering point for an interview: the eval dataset inherits the data-handling obligations of the data it was sampled from, it is not a lower-sensitivity artifact just because it is called test data.

### Synthetic generation that does not collapse

Naive synthetic generation asks a model for more examples like these and gets a cluster of near-duplicates around the easy centre of the distribution. Better: generate against an explicit schema of dimensions you want covered, for example query type crossed with document source crossed with difficulty, and sample the cells deliberately so the hard and rare cells are represented. Then have a human or a second model filter for realism, discarding cases no real user would send. The goal is coverage of the space, especially its corners, not fluency.

### Versioning and drift

Version the dataset the way you version a schema. Each eval run records which dataset version it ran against, so a score is only comparable to another score on the same version. When you add or retire cases, bump the version and re-baseline, because comparing a new model on v3 of the set to an old model on v2 is meaningless. Track input drift separately: periodically compare the distribution of recent production inputs against the dataset, and when they diverge, that is the signal to resample. A dataset that never changes is quietly going stale against a moving world (as of 2026, re-check your tooling for drift detection).
